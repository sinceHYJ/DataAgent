● 现在逻辑很清晰了。路由到 PythonGenerateNode 的完整链路如下：

  路由到 PythonGenerateNode 的机制

  路由到 PythonGenerateNode 不是由 Dispatcher 直接判断的，而是由 LLM 在 
  PlannerNode 中动态决定的。完整链路是：

  1. PlannerNode 调用 LLM 生成执行计划

  PlannerNode 调用 LLM，传入 Planner Prompt（planner.txt），LLM 根据用户问题和
  Schema 自行判断需要哪些步骤，输出一个 Plan JSON 对象：

  {
    "thought_process": "分析思路...",
    "execution_plan": [
      { "step": 1, "tool_to_use": "SQL_GENERATE_NODE", ... },
      { "step": 2, "tool_to_use": "PYTHON_GENERATE_NODE", ... },
      { "step": 3, "tool_to_use": "REPORT_GENERATOR_NODE", ... }
    ]
  }

  2. PlanExecutorNode 读取计划逐步路由

  PlanExecutorNode（PlanExecutorNode.java:98-101）按当前步骤号读取
  executionStep.getToolToUse()，如果值是 "PYTHON_GENERATE_NODE"，就设置
  PLAN_NEXT_NODE = "PYTHON_GENERATE_NODE"：

  ExecutionStep executionStep = executionPlan.get(currentStep - 1);
  String toolToUse = executionStep.getToolToUse();
  return determineNextNode(toolToUse);

  3. PlanExecutorDispatcher 根据 PLAN_NEXT_NODE 路由

  Dispatcher 读取 PLAN_NEXT_NODE，匹配到 "PYTHON_GENERATE_NODE" 就路由过去。

  LLM 在什么情况下会生成 PYTHON_GENERATE_NODE？

  根据 planner.txt Prompt 的指导，LLM 在以下场景会选择 Python：

  ┌──────────────┬───────────────────────────────────────────────────────────┐
  │     场景     │                           示例                            │
  ├──────────────┼───────────────────────────────────────────────────────────┤
  │ 复杂计算     │ 环比/同比增长率、排名、相关性分析、统计检验               │
  ├──────────────┼───────────────────────────────────────────────────────────┤
  │ 数据可视化   │ 绘制柱状图、折线图、散点图等图表                          │
  ├──────────────┼───────────────────────────────────────────────────────────┤
  │ SQL难以实现  │ 跨数据集联合计算、复杂的数据清洗和转换                    │
  ├──────────────┼───────────────────────────────────────────────────────────┤
  │ 用户明确要求 │ 用户反馈中提到"需要用Python"时（Prompt                    │
  │              │ 中标注为最高优先级）                                      │
  └──────────────┴───────────────────────────────────────────────────────────┘

  NL2SQL 模式下不会路由到 Python

  当 IS_ONLY_NL2SQL = true 时（PlannerNode.java:55-57），PlannerNode
  直接返回硬编码的单步 SQL 计划，完全跳过 LLM 规划，自然不会出现 Python 步骤。

  简化流程图

  PlannerNode
      │
      ├─ IS_ONLY_NL2SQL=true → 硬编码: [SQL_GENERATE_NODE] → END
      │
      └─ IS_ONLY_NL2SQL=false → LLM根据Prompt动态生成多步Plan
                                     │
                                     ▼
                              PlanExecutorNode (逐步执行)
                                     │
                       读取当前 step 的 toolToUse
                       ┌──────────────┼──────────────┐
                       ▼              ▼              ▼
                SQL_GENERATE_NODE  PYTHON_GENERATE_NODE  REPORT_GENERATOR_NODE

  总结：Python 步骤完全由 LLM 在规划阶段自主决定，系统本身没有硬编码的规则来触发
   Python——Planner Prompt 告诉 LLM "SQL 难以满足需求时用
  Python"，具体的判断交给模型。
